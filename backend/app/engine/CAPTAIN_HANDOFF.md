# Капитану и его ИИ: подключение части участника 2

Задача: подключить готовые данные и алгоритм участника 2 к существующему API
и согласовать frontend с API. Сначала прочитай `MVP_SPEC_QOR_AI.md`,
`docs/INTEGRATION.md`, `backend/app/contracts.py` и этот документ.
Не создавай второй сервер и не заменяй расчёт фикстурами.

## Что уже готово

- `app.engine.service.calculate(dataset, params) -> EngineResult` использует
  общие контракты `app.contracts` и реальный детерминированный алгоритм
  `qor-mvp-1.0`. Учитывает параметры расчёта, категорию и сценарий.
- `app.importers.service.import_dataset(request) -> DatasetPayload` читает
  шесть XLSX одного поставщика, проверяет схемы, SHA-256 и область данных,
  сохраняет нормализованные данные и происхождение ячеек.
- Внутренние модели движка остаются внутри модуля. HTTP получает общие
  `Recommendation`, `Factor`, `EngineResult`; контракт капитана не изменён.
- Пересчёт работает без исходных временных файлов. ID строк поставок уникальны
  во всём наборе, количества в индексе поставок приведены к складским единицам.
- `backend/tests/test_services.py` проверяет настоящие модули через API:
  импорт → расчёт → сценарий → объяснение без LLM → заказ → правка → approve → CSV,
  а также сохранение набора после перезапуска приложения.

## 1. Окружение

Из корня проекта установи зависимости в общее Python 3.12 окружение:

```sh
uv venv .venv --python 3.12
uv pip install --python .venv/bin/python -r backend/requirements-dev.lock -r backend/requirements-engine.txt
.venv/bin/python -m pytest
```

Если `.venv` уже существует, используй его без пересоздания.
В локальном `.env` выставь:

```dotenv
ENGINE_MODULE=app.engine.service
IMPORTER_MODULE=app.importers.service
```

Остальные настройки API сохрани. Ключи не добавляй в Git.
Сами сервисы расчёта и импорта не требуют OpenAI/NVIDIA и не обращаются к сети.
Подключение LLM остаётся в существующем слое `app.ai`; вызов платной модели
в проверках участника 2 не выполнялся.

## 2. Подключи синтетический набор к настоящему движку

Одних переменных окружения недостаточно: `demo-platform-v1` зарегистрирован
с `backend="fixture"` и продолжает вызывать платформенную фикстуру.

В `backend/app/main.py` добавь импорт:

```python
from .engine.service import DEMO_DATASET_ID, demo_dataset
```

В существующем `lifespan`, после `store.init()` и до `yield`, добавь:

```python
if not store.get("dataset", DEMO_DATASET_ID, "public"):
    store.put(
        "dataset", DEMO_DATASET_ID, "public",
        {"backend": "plugin", "dataset": demo_dataset().model_dump(mode="json")},
    )
```

Этот шаг должен выполнить капитан: изменения его `main.py` участник 2
не вносил. Для демонстрации выбирай `demo-engine-v1`. В нём восемь товаров,
дата `2026-09-22`, склад `synthetic-almaty`, поставщики `iek` и `systeme_electric`.
Старые сохранённые наборы не мигрируются автоматически при изменении генератора;
при изменении схемы/данных нужно версионировать ID набора.

## 3. Контрольный проход через API

1. Запусти `.venv/bin/python run.py --port 8000`.
2. Создай сессию через `POST /api/sessions`; используй выданный Bearer token.
3. Проверь `GET /api/datasets`: `demo-engine-v1` должен иметь backend `plugin`.
4. Вызови `POST /api/runs`:

```json
{
  "dataset_id": "demo-engine-v1",
  "supplier_id": "systeme_electric",
  "as_of": "2026-09-22",
  "lead_time_days": 14,
  "review_days": 7,
  "safety_days": 7
}
```

5. Убедись, что `algorithm_version="qor-mvp-1.0"`, `data_mode="synthetic"`,
   для SKU `00001` рекомендовано **156** штук.
6. Через `GET /api/datasets/demo-engine-v1/shipments` возьми ID строки
   поставки SKU `00001`. Не конструируй ID вручную.
7. Отправь `POST /api/runs/{run_id}/scenario` с этим `shipment_id`,
   `delay_days=30`, `demand_change_pct=0`. Для SKU `00001` получится **204**.
   Другие строки поставок не сдвигаются; повторный сценарий не накапливает задержку.
8. Из исходного расчёта создай заказ на SKU `00001`, измени количество на **168**
   с причиной и актуальной версией, утверди с подтверждением предупреждений,
   экспортируй CSV. Проверь ведущие нули SKU и количество 168.
9. Для кабеля проверь единицы: 2 бухты по 305 м. Для товара с неизвестными
   данными проверь блокировку утверждения даже после ручного ввода количества.

Точные тела запросов заказов смотри в `/api/docs` и
`test_real_plugins_through_captain_import_calculate_approve_export`.
Обычный `scripts/smoke.py` на платформенной фикстуре сам по себе
не доказывает подключение движка участника 2.

## 4. Проверка загрузки Excel

```sh
PYTHONPATH=backend .venv/bin/python -m app.importers.demo_files --output-dir data/demo/xlsx
```

Генератор создаёт 12 синтетических книг: по шесть для каждого поставщика.
Загружай через `POST /api/imports` шесть XLSX выбранного поставщика с Bearer
и `X-Admin-Token`. Поля формы:

- `supplier_id`: `iek` или `systeme_electric`;
- `mapping_version`: `qor-explicit-xlsx-v1`;
- `as_of`: `2026-09-22`;
- `warehouse_id`: `synthetic-almaty`.

Дождись `completed` через `GET /api/imports/{id}`, возьми `dataset_id`,
создай расчёт. В API загруженный набор имеет `mode="real"` согласно контракту,
даже если для проверки загружены наши синтетические книги. Клиент загрузки
не может сам объявить набор публичным. Для публичного синтетического демо
используется доверенный серверный `demo_dataset()` из раздела 2.

**Ограничение:** профиль требует скрытый лист `_QOR_IMPORT` с явной схемой;
генератор уже его добавляет. Произвольные реальные выгрузки IEK/Systeme
без подготовленных схем не поддерживаются этим профилем. Реальные исходники
не предоставлены. Для них участник 2 должен настроить и проверить сопоставления
листов/колонок, единиц, периода и покрытия данных. CSV этим профилем не поддерживается.
Не выдавай прохождение синтетических тестов за проверку 12 реальных форматов.

## 5. Согласуй frontend с API вместе с участником 3

Проверь существующий клиент и добавь явные преобразования при необходимости:

- Авторизация: Bearer из `/api/sessions`; сервер не использует cookie-сессию.
- Списки: извлекай `items` из ответа, не считай ответ массивом.
- Поставщики: используй ID из dataset. В публичном демо это `systeme_electric`,
  а не UI-псевдоним `systeme`. Каждый расчёт относится к одному поставщику.
- `risk_status`: `ok/warning/critical/unknown`;
  `data_status`: `ready/review/blocked`; причины блокировки — `approval_blockers`.
- График: `trajectory` с `date/without_order/with_order/incoming/demand`.
  История: `month/actual/regular/restored/stockout_days/complete/source`.
- Факторы: `id/label/value/unit/status/source`. Отображай источник и допущения.
- Сводка API: `products/to_order/critical/needs_review`.
- Создание заказа использует `run_id/supplier_id/skus`; правки отправляются
  отдельным PATCH с `version/changes`. Approve требует актуальную версию
  и подтверждение предупреждений. Ручная правка не снимает блокеры данных.
- Для разбора сценария передавай требуемый API `run_id`; для неоднозначной
  поставки запрашивай выбор пользователя.

`engine/examples/table.json` — прежний пример внутреннего формата движка,
не эталон HTTP-контракта. Эталон — `app.contracts`, OpenAPI и тесты сервисов.
Если неизвестны MOQ/кратность, общий контракт требует технические значения
0/1: реальные факторы остаются `null`, присутствуют блокеры и предупреждение.
Не показывай эти технические значения как подтверждённые правила поставщика.

## Граница выполненного

Сервисы участника 2 и интеграционные тесты готовы. Капитану осталось подключить
публичный plugin-набор и настройки, согласовать UI, выполнить сквозную проверку
в браузере и отдельно проверить выбранного LLM-провайдера. Реальные Excel,
нагрузка на больших выгрузках и качество прогноза на реальных данных ещё
не проверены. Не меняй алгоритм или общий контракт ради обхода ошибки UI:
сначала проверь преобразования, единицы и выбранный backend набора.
