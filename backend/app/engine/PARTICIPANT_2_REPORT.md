# Участник 2 — документация выполненной работы

Состояние на 23.09.2026. Основание: `MVP_SPEC_QOR_AI.md`, разделы 6, 11 и 13.
Участник 2 отвечает за данные и алгоритм. Его результат — воспроизводимый
расчёт закупки и паспорт каждой рекомендации.

Пути ниже указаны относительно корня репозитория. Это описание фактически
реализованного кода; проверка на синтетических данных не означает проверку
реальных форматов поставщиков.

## 1. Что делает моя часть

Модуль читает Excel, объединяет сведения о товаре, оценивает регулярный спрос,
учитывает сезонность, рост, остаток и своевременные поступления. Возвращает
количество для закупки, риск дефицита, историю, график будущего остатка,
факторы расчёта и предупреждения.

Путь данных:

```text
Excel → importer.service → DatasetPayload → хранение в API капитана
                                               ↓
                              engine.service + параметры сценария
                                               ↓
                              EngineResult → API → интерфейс
```

Пользователь проверяет рекомендацию и утверждает заказ через API капитана.
Расчётный модуль не отправляет заказ поставщику и не принимает решение за человека.

## 2. Задачи, реализация и расположение кода

### 2.1. Окружение и зависимости

Подготовлены зависимости, закреплённые версии и инструкции запуска.

- `backend/.python-version` — версия Python для части данных.
- `backend/requirements-data.in` — исходный список зависимостей.
- `backend/requirements-data.lock` — закреплённые версии и хеши.
- `backend/requirements-engine.txt` — зависимости движка для общего backend.
- `backend/DATA_ENVIRONMENT.md` — инструкция по окружению.
- `.env.example`, `.gitignore` — пример настроек и исключение секретов/локальных данных.

Используется Python 3.12, `uv` для окружения, Pydantic для проверки структур,
openpyxl для Excel, pytest для тестов. NumPy и pandas включены в зависимости
части данных, но текущий алгоритм рассчитывается средствами стандартной
библиотеки Python: `statistics`, `datetime`, `calendar`, `collections`, `math`.
Обученной ML-модели и GPU в этом модуле нет.

### 2.2. Два адаптера и 12 источников

Файл: `backend/app/importers/xlsx.py`.

- `IEKAdapter`, `SystemeElectricAdapter` — адаптеры поставщиков.
- `WorkbookMapping`, `WideColumn` — явные схемы листов, заголовков и колонок.
- Шесть типов на поставщика: продажи, месячные продажи, месячные остатки,
  поставки в пути, сезонность, MOQ.
- SKU сохраняются строками, включая ведущие нули; пустое значение не заменяется нулём.
- Отрицательная операция не превращается в продажу через модуль числа.
- Формулы Excel не исполняются; отсутствие сохранённого результата отмечается.
- `CellTrace` сохраняет происхождение: файл, хеш, лист, строку, поле и преобразование.
- `ImportBatch` предотвращает повторное добавление одного файла в набор.

Использовано: openpyxl, Pydantic, SHA-256. Все 12 источников проверены
на синтетических книгах. Реальные исходники не предоставлены.

### 2.3. Нормализация и объединение

Файл: `backend/app/importers/assemble.py`, функция `assemble_products`.

Источники соединяются по поставщику, SKU и складу. Проверяются единицы,
правила заказа, полнота детализации и поступлений. Отдельный справочник MOQ
имеет приоритет; конфликты отражаются в результате или требуют исправления.
Детальная и месячная история не суммируются дважды. Месячный снимок остатка
не объявляется текущим наличием или точным периодом отсутствия товара.

Структуры: `backend/app/engine/models.py` — `ProductInput`, `Sale`, `Inventory`,
`Shipment`, `Source`, политики и результаты. Pydantic проверяет типы и ограничения.

### 2.4. Разовые крупные покупки

Файл: `backend/app/engine/demand.py`, функция `clean_orders`.

Продажи сначала объединяются по документам. Размер покупки сравнивается
с устойчивой историей через медиану и MAD — медиану абсолютных отклонений.
Аномальная часть отделяется от регулярной потребности; сохраняются исходное
значение и причина корректировки. При наличии обезличенного клиента
проверяется концентрация его покупок за день и месяц.
Повторяющиеся повышения спроса проверяются отдельно, чтобы не удалить устойчивый рост.

Это защищает расчёт от завышенного заказа после одной крупной проектной покупки.
Пороги — документированные эвристики MVP, требующие проверки на реальных данных.

### 2.5. Восстановление спроса при stockout

Файл: `backend/app/engine/demand.py`, `reconstruct_demand`, `build_history`.

Используются явно заданные интервалы отсутствия. Пересекающиеся дни не считаются
дважды. После очистки разовых покупок спрос восстанавливается по периоду наличия;
при недостатке дней используется доступная историческая опора либо результат
остаётся неизвестным. Контрольный случай: 200 продаж за 20 дней наличия
и 10 дней отсутствия → оценка 300 за месяц.

Восстановленный спрос является оценкой, а не доказанным объёмом потерянных продаж.

### 2.6. Сезонность и рост

Файл: `backend/app/engine/demand.py`, `forecast_level`, `build_history`.

Учитываются 12 месячных сезонных коэффициентов, базовый дневной спрос,
сопоставимая история и рост. Подтверждённый прирост заменяет оценённый.
Для короткой истории предусмотрен запасной способ оценки; один и тот же рост
не применяется повторно. Сценарное изменение спроса задаётся отдельно.

### 2.7. Расчёт закупки, поставки, категория и округление

Файл: `backend/app/engine/calculator.py`, `calculate`, `round_order`.

```text
горизонт = срок поставки + период пересмотра
потребность = max(0, прогноз + страховой запас − остаток − своевременные поступления)
заказ = округление потребности после перевода в единицы заказа с учётом MOQ и кратности
```

Учитываются подтверждённые поступления, попадающие в горизонт. Задержка
конкретной партии меняет расчёт и/или дату дефицита. Подтверждённая политика
категории может уточнять параметры запаса; числовые коды категорий не получают
выдуманную бизнес-семантику.

Контрольные примеры: 156 штук в базовом случае, 204 после задержки поставки;
потребность 400 м при 305 м в бухте → 2 бухты. Нулевая потребность остаётся нулевой.
Неизвестные критичные данные приводят к блокировке утверждения.

### 2.8. Паспорт рекомендации

Файлы: `backend/app/engine/calculator.py`, `models.py`, `service.py`.

Каждая рекомендация содержит количество, единицы, остаток, прогноз,
страховой запас, учтённые поступления, риск и дату дефицита, факторы с источниками,
предупреждения и причины блокировки. Доступны история и дневная траектория
остатка с новым заказом и без него. Базовое объяснение строится без обращения к LLM.

### 2.9. Подключение к контракту капитана

- `backend/app/engine/service.py`:
  `calculate(dataset, params) -> EngineResult`.
- `backend/app/importers/service.py`:
  `import_dataset(request) -> DatasetPayload`.
- Общие типы: `backend/app/contracts.py` — принадлежат общей части команды.

Расчёт чистый: не меняет входной набор, не обращается к сети или базе.
Импорт возвращает самодостаточный JSON-совместимый набор, который можно сохранить
и пересчитать после удаления временных файлов. ID строк поставок уникальны.

Профиль импорта `qor-explicit-xlsx-v1` требует явную схему на скрытом листе
`_QOR_IMPORT`. Генератор добавляет её автоматически. Произвольные Excel без
настроенной схемы и CSV этим профилем не поддерживаются.

Инструкция интеграции: [CAPTAIN_HANDOFF.md](CAPTAIN_HANDOFF.md).
После обновления `main` до `76bc20f` капитан уже добавил автоматическую
регистрацию `demo-engine-v1` с backend `plugin`. `demo-platform-v1` остаётся
фикстурой. Текущий обзор интеграции: `docs/BACKEND_LOGIC_REVIEW.md`.

### 2.10. Синтетические данные

Случаи: стабильный спрос, сезонность, рост, разовая покупка, stockout,

## 3. Кто подключает базу данных

**База данных — ответственность капитана. Участник 2 не должен добавлять
собственное соединение с БД в алгоритм или создавать вторую базу.**

В проекте уже реализовано SQLite-хранилище:

- `backend/app/storage.py`, класс `Store` — соединения, таблицы, чтение и запись;
- `backend/app/main.py` — создание `Store`, `store.init()` при запуске,
  сохранение объектов API;
- `backend/app/config.py` — настройки `QOR_DATA_DIR` и `DATABASE_PATH`.

По умолчанию файл — `data/qor.sqlite3` при запуске из корня с настройками
по умолчанию. `DATABASE_PATH` может задать другой путь. SQLite не требует
отдельного сервера БД. Таблица `objects` хранит JSON-объекты с владельцем
и версией, `sessions` — сессии с хешами токенов. Защита версий предотвращает
перезапись черновика устаревшим изменением.

Моя обязанность: вернуть корректные `DatasetPayload` и `EngineResult`.
Обязанность капитана: сохранить наборы, расчёты и заказы, настроить доступ,
постоянный каталог/том при развёртывании и проверить сохранность данных.

## 4. Кто делает ИИ и утверждение

Капитан отвечает за `backend/app/ai`, сетевой вызов OpenAI/NVIDIA,
проверку ответа, API сценариев и утверждения. Участник 3 отвечает за интерфейс.
Моя часть предоставляет рассчитанные факты и объяснение.

ИИ объясняет рекомендацию и преобразует фразу в параметры сценария.
Точное количество считает алгоритм; окончательное решение принимает человек.
Сохранение утверждённого заказа и CSV уже реализованы в платформенной части
(`backend/app/main.py`, `backend/app/orders.py`) и проверены с нашими сервисами.
