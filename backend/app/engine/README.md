# QOR AI: модуль участника 2

Владелец этой части — **участник 2: данные и алгоритм**. Модуль реализует
раздел 6 ТЗ и предоставляет локальный контракт для интеграции капитаном.
Общий API-контракт команды не меняется этим модулем.

## Запуск из корня репозитория

Окружение устанавливается по `backend/DATA_ENVIRONMENT.md`.

```sh
PYTHONPATH=backend backend/.venv/bin/python -m app.engine.demo --output-dir data/demo
PYTHONPATH=backend backend/.venv/bin/python -m app.importers.demo_files --output-dir data/demo/xlsx
PYTHONPATH=backend backend/.venv/bin/python -m pytest backend/tests -q
```

Первая команда создаёт нормализованный `dataset.json`, полные результаты
`recommendations.json` и `table.json` для таблицы фронтенда. Вторая создаёт
12 синтетических XLSX, явные схемы в `manifest.json`, отчёт качества и
результаты расчёта после импорта. Все данные демонстрационные, с фиксированной
датой 22.09.2026 на конец дня и синтетическими клиентскими ID.
Версионированная копия ответа для начала работы фронтенда находится в
`examples/table.json`; её можно использовать до подключения API. После
изменения расчёта её следует регенерировать той же командой и обновить копию.

Восемь товаров: стабильный, сезонный, растущий, с разовой покупкой,
с точным stockout, с задержкой поставки, кабель с переводом в бухты и товар
с недостаточными данными. Профиль сезонности един для каждого поставщика
внутри этого демонабора. Значения не являются условиями реальных поставщиков.
Генераторы находятся в Git; созданные файлы лежат в игнорируемой папке `data/`.

## Вызов из API

```python
from app.engine import ProductInput, Scenario, calculate
from app.engine.demo import AS_OF, make_demo_products

product = make_demo_products()[0]
baseline = calculate(product, as_of=AS_OF)
scenario = Scenario(shipment_delays={product.incoming[0].shipment_id: 30})
changed = calculate(product, as_of=AS_OF, scenario=scenario)
assert baseline.recommended_qty == 156
assert changed.recommended_qty == 204
response = changed.model_dump(mode="json")

# Для сохранённого нормализованного объекта:
restored = ProductInput.model_validate(product.model_dump(mode="json"))
```

`calculate` не читает `.env`, не обращается к сети/БД, не меняет входные данные
и не использует системную дату. `calculate_many` принимает набор товаров,
проверяет уникальность ключа поставщик + SKU + склад и сортирует результат
по риску. Политики, дата расчёта, единицы и источники передаются явно.

Капитан передаёт функции дату набора в виде `datetime.date` после приведения
бизнес-даты к UTC+5. Перевод текста в `Scenario`, сохранение версии расчёта,
сессии, утверждение и CSV относятся к API. Наличие API-ключа расчёту не нужно.

## Входной контракт

Схемы находятся в `models.py`. Числа должны быть конечными, SKU — строкой.
Коды с ведущими нулями сохраняются. Неизвестные значения передаются как `None`.

- Один `ProductInput` представляет один SKU одного поставщика на одном складе.
- Количества продаж и месячной истории заранее приведены к `stock_unit`.
- `detail_months` — явно подтверждённое полное покрытие месяца детализацией.
  Отсутствие строки в неполном источнике не интерпретируется как ноль.
- `monthly_sales` — резервные месячные итоги, не прибавляемые к детализации.
- `Inventory.available` уже учитывает резерв; при его отсутствии нужны оба
  поля `on_hand` и `reserved`. Старый снимок используется только после явного
  ручного подтверждения и с предупреждением. Будущий снимок не используется.
- `incoming_complete=True` означает подтверждённую полноту списка поступлений,
  включая подтверждённый пустой список. По умолчанию полнота неизвестна.
- `moq` и `order_multiple` заданы в `order_unit`; коэффициент перевода означает
  число складских единиц в одной единице заказа.
- Категория хранится отдельно от подтверждённой политики. Код категории 1–7
  не интерпретируется автоматически. Без соответствия применяется явно
  отмеченное допущение: 7 страховых дней.
- `Source` содержит `origin` и статус `observed/estimated/assumed/missing`.
  Stockout задаётся закрытыми интервалами; оценочный сценарий передаёт
  `source.status="assumed"`. Пересекающиеся дни учитываются один раз.

## Выход и единицы

Все поля минимальной строки из раздела 9 ТЗ присутствуют в `Recommendation`.
`available_stock`, `eligible_incoming`, `forecast_qty`, `safety_stock`,
`raw_need` и `recommended_stock_qty` заданы в `stock_unit`.
`recommended_qty` задан в `unit`, равном `order_unit`.
`stockout_date` — первая дата отрицательного прогнозного остатка без нового
заказа; точное исчерпание до нуля к концу дня ещё не означает неудовлетворённый спрос.

Дополнительные данные:

- `history`: исходные, регулярные и восстановленные месячные продажи,
  число дней отсутствия и признак завершённого месяца;
- `adjustments`: агрегированные документы, исключённая часть, причины,
  синтетический клиентский ID и ссылки на источник;
- `trajectory`: дневной спрос, поступления и остаток с новым заказом/без него;
- `factors`: значения паспорта с единицами, источниками и статусами;
- `warnings`: стабильные коды предупреждений для подписей в интерфейсе;
- `approval_blockers`: причины, которые API обязан проверить перед утверждением.

`data_status=preliminary` не означает блокировку сам по себе. Для утверждения
список `approval_blockers` должен быть пустым. Неизвестный актуальный остаток,
единицы, правила заказа или история требуют дополнительных данных;
проектная категория требует отдельного подтверждения. Пересчёт после исправления
данных создаёт новую версию в API. Ручной ввод количества не должен обходить
проверку неизвестных единиц.

## Алгоритмические решения и ограничения

1. Продажи агрегируются по документу и дате. Отрицательные движения сохраняются
   на входе, исключаются из регулярного спроса и отмечаются для уточнения политики.
2. Для заказа используются предшествующие 180 дней положительных размеров:
   минимум 8 наблюдений, порог `max(5 * median, median + 6 * MAD)`.
   Разовая часть заменяется обычным размером, исходная операция сохраняется.
3. Клиентские покупки дополнительно группируются по дням и завершённым месяцам.
   Для месячной проверки принят отдельный параметр MVP: минимум 3 предыдущих
   месяца в окне 730 дней. Это допущение, требующее калибровки на реальных данных.
4. Кандидаты в трёх разных календарных неделях в пределах 180 дней сохраняются
   как возможный устойчивый рост с предупреждением. Ручная классификация
   `Scenario.order_classification` использует ID документа в области выбранного SKU.
5. Stockout компенсируется после очистки разовых покупок. При менее чем 7 днях
   наличия используются до трёх предыдущих завершённых сопоставимых месяцев
   с сезонной поправкой; при отсутствии опоры оценка остаётся неизвестной.
6. База — медиана дневных скоростей после устранения сезонности по минимум
   трём доступным месяцам предыдущего года. Рост — медиана отношений минимум
   двух из последних трёх месяцев к прошлому году. Подтверждённый прирост
   заменяет эту оценку. При короткой истории текущий уровень уже включает рост,
   дополнительное изменение задаётся только сценарием.
7. Горизонт — срок поставки + период пересмотра. Страховой запас — прогноз
   на страховые дни непосредственно после горизонта. Учитываются только
   подтверждённые поступления после даты расчёта и до конца горизонта включительно.
   Просроченные партии требуют сверки и блокируют утверждение.
8. Заказ округляется вверх после перевода единиц. Нулевая потребность остаётся
   нулевой. Если дефицит наступит раньше срока нового заказа, результат сообщает
   о необходимости ускорения; обычный заказ не скрывает ранний дефицит.

Исходные реальные Excel отсутствуют. Импорт проверен только на синтетических
книгах с явными схемами. Качество прогнозов на реальных данных, скорость первого
импорта 250 тысяч строк и выполнение на Linux AMD64 ещё не измерены.
Документированные эвристики не являются обученной моделью или доказательством экономии.
