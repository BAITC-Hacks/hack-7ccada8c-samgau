# Файловый обмен с 1С

Реализован путь: **исходные XLSX → импорт → расчёт → проверка человеком → утверждённый CSV**. Прямого подключения к базе 1С нет. Формат CSV описан ниже; совместимость с обработкой загрузки конкретной конфигурации 1С подтверждается только пробным импортом в тестовую базу.

## Капитану: запуск

1. Создать `.env` из `.env.example`. По умолчанию `IMPORT_ACCESS=admin`: импорт API требует `ADMIN_TOKEN`. Владелец может разрешить `IMPORT_ACCESS=session` для загрузки из интерфейса без ручного ключа; этот режим допускает загрузку любым посетителем в его собственную сессию.
2. Запустить `docker compose up --build -d` из корня. Общий Compose теперь собирает React из `frontend`, Caddy проксирует `/api` в FastAPI. SQLite и загрузки сохраняются в `qor_data`.
3. Открыть `http://localhost:8080`, раздел **Обмен с 1С**. На Linux для публичного HTTPS задать домен в `SITE_ADDRESS`, `HTTP_PORT=80`, `HTTPS_PORT=443` и направить DNS на сервер.
4. Выбрать поставщика, шесть XLSX из его папки и нажать **Проверить и загрузить**. Сессионный bearer передаётся автоматически и сохраняется в `sessionStorage` текущей вкладки.
5. После завершения открыть загруженный набор, проверить качество и рекомендации, утвердить выбранные позиции и скачать CSV. Данные импорта доступны только сессии загрузившего пользователя. Жюри может пользоваться публичными синтетическими наборами, чужие реальные загрузки ему не раскрываются.

Для локальной разработки: `python run.py` и в отдельном терминале `cd frontend`, `npm ci`, `npm run dev`. Python 3.12+, зависимости `backend/requirements-dev.lock` и `backend/requirements-engine.txt`. На машине автора создан локальный игнорируемый `.env`; его ключ не опубликован.

При `IMPORT_ACCESS=session` загрузка доступна любой действующей сессии сайта, включая посетителей публичной демонстрации. Данные изолированы по сессиям; ограничения — 64 MiB, один одновременный импорт, 4 попытки в минуту на сессию и 20 на сервер. Если нужен закрытый импорт, задайте `IMPORT_ACCESS=admin` и `ADMIN_TOKEN`: тогда загрузка доступна только API-клиентам с `X-Admin-Token`, а интерфейс покажет отказ сервера. Секреты в браузер не передаются.

## Профиль оригинальных файлов

`mapping_version=hackalem-2026-v1`, `as_of=2026-09-22`, `warehouse_id=Все склады`, `supplier=iek` либо `systeme_electric`.

Профиль привязан к исходной структуре и дате предоставленного комплекта. Он не выдаётся за импорт любой выгрузки 1С. Для другого формата остаётся существующий `qor-explicit-xlsx-v1` с явной картой столбцов.

| Источник | Использование |
| --- | --- |
| Динамика продаж | Код 1С, дата, документ, подписанное движение, единица. Отрицательное расходное движение преобразуется в положительную продажу; возвраты сохраняются со знаком. |
| Продажи по месяцам | Канонические месячные итоги. Детализация заменяет итог только при сверке сумм полного месяца, без удвоения продаж. |
| Остатки по месяцам | Единицы, история остатков и аудит. Начальный месячный остаток не подменяет актуальный свободный. |
| Товар в пути | Датированные партии. У Systeme также используются «Свободный остаток», «Остаток», «Зарезервировано». Пустые количества не означают ноль. |
| Сезонность | Готовый столбец `СЕЗОННОСТЬ` L11:L22 с рассчитанными значениями. Это оценка, включающая прогнозные месяцы, а не наблюдаемый факт по каждому SKU. |
| MOQ | Отдельный каталог, артикулы и правила. В этом MVP минимум и шаг приняты равными значению MOQ/кратности и явно требуют просмотра предупреждений. |

Допущения и ограничения:

- Сводные файлы не разделены по складам. Отображается «Все склады»; нельзя переименовать этот охват в «Алматы» и утверждать, что расчёт выполнен по одному складу.
- В динамике нет идентификатора покупателя. Проверка концентрации разового заказа у одного клиента невозможна; это отражено в предупреждениях.
- Месячные остатки не дают точных дней отсутствия товара. Они сохраняются в `monthly_stock_audit`; точные stockout-интервалы не выдумываются.
- Для `шт` приняты одинаковые складские и закупочные единицы. Для метров, бухт и неустановленных единиц заказ блокируется до явного согласования пересчёта. Коэффициент не извлекается догадкой из названия.
- Ошибки Excel остаются неизвестными значениями. Одинаковые MOQ учитываются один раз; конфликтующие правила блокируют заказ. Строки без текстового кода перечислены в качестве данных.
- Пустые ячейки в пути не подтверждают отсутствие поставок: для таких SKU покрытие поступлений неизвестно. Даже после добавления остатка IEK может требоваться сверка поступлений и правил в явном профиле.
- Параметры поставки по умолчанию: 14 дней, пересмотр 7 дней, страховой запас 7 дней. Они являются допущениями расчёта, а не извлечёнными договорными сроками.

## Дополнительный актуальный остаток

Можно добавить седьмым файлом `inventory.csv` (UTF-8, разделитель `;`). Пустой шаблон скачивается на экране. Заголовок строго:

```csv
sku_1c;stock_unit;available_stock;as_of;warehouse_id
```

Заполнять подтверждённые свободные остатки, дату `2026-09-22` и охват `Все склады`. Код — текст, с сохранением ведущих нулей и подчёркиваний. Ноль допустим, пустое значение нет. Неизвестный код, дубликат, другая дата, охват или единица отклоняются. Файл не снимает другие блокировки качества данных.

## Выходной CSV

Endpoint `GET /api/orders/{draft_id}/export.csv`, только после утверждения. UTF-8 с BOM, `;`, CRLF, защита от формул в ячейках.

| Поле | Назначение для обработки 1С |
| --- | --- |
| `supplier_id` | Идентификатор поставщика, требуется сопоставление со справочником 1С |
| `sku_1c` | Точное текстовое значение кода номенклатуры |
| `supplier_article`, `name` | Контрольные артикул и наименование, не ключ сопоставления |
| `order_unit`, `quantity` | Закупочная единица и утверждённое количество |
| `stock_unit`, `stock_equivalent` | Складская единица и результат пересчёта |
| `warehouse_id`, `as_of` | Охват и дата снимка; «Все склады» не является ссылкой на склад 1С |
| `reason`, `risk`, `version` | Обоснование, риск и версия заказа |
| `editor_role`, `editor_id` | Аудит изменений внутри QOR |
| `data_mode` | `real`, `synthetic`, для старого заказа без признака — `unknown` |

Числа записаны с десятичной точкой без разделителей тысяч. При загрузке не позволять Excel автоматически превращать коды в числа. Это файл рекомендаций, без автоматического проведения документа, цен, договоров, налогов и отправки поставщику.

**Что осталось со стороны 1С:** назвать конфигурацию и обработку загрузки, сопоставить поставщика, номенклатуру, единицы, организацию и целевой склад документа; проверить одну строку и один товар с пересчётом единиц в тестовой базе. Для «Все склады» сначала определить распределение закупки. Только после этого можно заявлять подтверждённую совместимость с учётной системой партнёра.

## Изменения контракта интерфейса

Frontend теперь использует общий bearer, `{items}` в `/datasets`, отдельный run на поставщика, канонические поля рекомендаций, nullable-значения и складские/закупочные единицы. Составной ID расчёта и ключ товара существуют только внутри клиента; в серверные пути передаются настоящие run ID и исходный SKU. Сценарий задержки выбирает конкретную партию. Заказ проходит create → PATCH изменений → approve с подтверждением предупреждений → CSV. Повтор утверждения после ошибки использует уже созданный черновик.

## Проверки

Тест `backend/tests/test_partner_exchange.py` проверяет полный HTTP-путь на синтетических файлах исходной структуры: импорт без ручного ключа и совместимость режима admin, изоляцию сессий, расчёт, запрет экспорта без утверждения, подтверждение предупреждений и чтение CSV с неизменным кодом 1С. Тесты frontend проверяют multipart, bearer, пагинацию и сохранение неизвестных значений.

На предоставленных локальных оригиналах: импорт Systeme — 724 SKU, 33 позиции с положительным заказом без блокировок при параметрах по умолчанию; IEK — 3183 SKU. Оригиналы и производные данные остаются в игнорируемом `data/`, в Git не публикуются. Импорт в настоящую базу 1С и запуск Docker Engine на сервере партнёра не проверялись.
