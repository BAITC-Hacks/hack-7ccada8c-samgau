## 1. Что готово и что пока не соединено

Дополнение: обзор содержит `frontend/src/components/WarehouseScene.tsx` — кликабельную CSS 3D-схему по текущим `rows`, с фильтрами и переходами в паспорт/сценарий. Отдельного endpoint для неё не нужно. При интеграции статусов, составных SKU и складских единиц обновить и этот компонент; сейчас он использует прежний UI-контракт. Геометрия не описывает реальную вместимость или размещение товаров.

Готовы экраны «Обзор склада», «План закупок», «Проверка данных», «Что, если…», «ИИ-помощник»; графики, поиск, фильтры, паспорт решения, ручная правка заказа, CSV, ошибки и загрузка. Расчётный backend и импортёр уже есть — их не нужно писать заново. Чат подключён к серверному адаптеру и работает со справкой без ключа; код вызова модели тоже реализован.

**Сейчас `frontend/src/lib/api.ts` не соответствует API 0.2.0.** Переключение «Данные API» само по себе не подключает рабочий склад. Основные проблемы:

- Общий клиент не отправляет Bearer. `credentials: include` не создаёт серверную сессию. Чат создаёт свою отдельную Bearer-сессию.
- UI ожидает массив datasets; сервер возвращает `{items}`.
- UI использует один run на обоих поставщиков, а backend создаёт run на одного.
- Различаются названия полей, статусы, модель графика, тело сценария и процесс утверждения заказа.
- В UI одна `unit` для всех чисел; в движке складские единицы отличаются от единиц заказа.
- Корневой Docker Compose раздаёт `deploy/web`, где пока нет сборки этого React. Отдельный `frontend/compose.yaml` запускает только демонстрационный web, без API.

Не маскировать ошибки переходом на демо, не подставлять 0 вместо неизвестных значений и не выводить «ИИ ответил», если сервер вернул fallback.

## 3. Архитектура интеграции — сохранить API, адаптировать клиент

Сохранить канонический backend 0.2.0 и математический движок участника 2. Основная работа — адаптер в `frontend/src/lib/api.ts`, общий модуль сессии и уточнение типов. Компоненты менять только там, где текущая форма не выражает серверную семантику: выбор партии, единицы, неизвестные значения, подтверждение предупреждений. Новый дизайн сохраняется.

Поток: React → same-origin `/api` → FastAPI → SQLite + движок. FastAPI → OpenAI/NVIDIA только для объяснений, разбора текста и чата. Количества заказа считает движок, а не LLM и не браузер.

Для общего обзора в клиенте нужен объект набора расчётов: `dataset_id`, `as_of`, `supplier_id → run_id`, исходные и сценарные run. Можно скрыть этот объект за локальным ключом внутри адаптера, но этот ключ **нельзя отправлять серверу как run_id**. Каждая карточка/строка должна сохранять настоящий `run_id`, исходный `sku` и поставщика. Для React selection/key используйте составной идентификатор, если SKU могут повторяться у разных поставщиков.

### P0. Сессия и первый расчёт

1. `POST /api/sessions` → `{token, token_type, session_id, expires_at}`. Хранить token в `sessionStorage`, переиспользовать после обновления страницы. Все рабочие запросы, включая CSV, идут с `Authorization: Bearer …`.
2. Вынести сессию в общий модуль для основного API и чата. При 401 не терять незавершённый заказ молчаливым созданием новой сессии; показать понятное действие «Начать новую сессию» и объяснить потерю доступа к прежним черновикам.
3. `GET /api/datasets` → брать `items`; выбирать `demo-engine-v1`, `engine_backend=plugin`. Это восемь синтетических случаев настоящего движка. Локальные 12 демотоваров UI и старая фикстура `demo-platform-v1` — другие наборы.
4. Использовать `supplier_ids` и `as_of` из dataset. Создать отдельный run для каждого поставщика, объединить отображение. Не отправлять `supplier_id: null` или `all`.

```json
POST /api/runs
{"dataset_id":"demo-engine-v1","supplier_id":"systeme_electric","as_of":"2026-09-22","lead_time_days":14,"review_days":7,"safety_days":7}
```

Для второго поставщика — `iek`. Ответ содержит `run_id`, `summary`, `algorithm_version`, `data_mode`, `warnings`. Приёмка ожидает `algorithm_version=qor-mvp-1.0`.

### P0. Карточка товара, графики, качество

`GET /api/runs/{run_id}/products/{sku}` возвращает полную Recommendation. Адаптер формирует нужный UI вид:

- `history` уже есть; сохранить хронологию, null, `complete`, различать фактический и очищенный спрос. Не рисовать отсутствующий месяц как нулевые продажи.
- `trajectory → projection`; `without_order → baseline` для исходного run.
- Для сценария `baseline` брать из **исходного** run, `scenario` — из `without_order` сценарного run, `with_order` — из сценарного run. Сопоставлять по ISO-дате, затем форматировать подписи. Копирование одной линии в обе скрывает эффект сценария.
- `method` сформировать из параметров run и версий алгоритма; не оставлять текст о локальном демонстрационном графике для реальных расчётов. Горизонт в заголовке брать из данных, а не жёстко 28 дней.
- `GET /api/datasets/{id}/quality` у demo-engine и штатного импортёра содержит `source_count`, `mapped_skus`, `issues`. Проверить форму, показывать warnings; у synthetic source_count=0 — это корректно, не подставлять 6.

### P0. Сценарий — обязательно выбрать реальную партию

UI сейчас предлагает задержку всех поставок поставщика, но backend принимает **одну партию**. Минимальное честное исправление: в `ScenarioModal.tsx` добавить выбор партии и подпись «Задержка выбранной поставки».

1. Получить `GET /api/datasets/{id}/shipments`, распаковать `items`, отфильтровать по поставщику.
2. Показать артикул, количество, дату партии. `shipment_id` брать из ответа, не конструировать. Он может содержать `/`.
3. Для задержки требовать явный выбор партии. Не брать первую автоматически и не выдавать изменение одной партии за задержку всего поставщика.
4. `POST /api/runs/{base_run_id}/scenario` с `{"shipment_id":"…","delay_days":7,"demand_change_pct":20}`. Поле `supplier_id` в теле запрещено.
5. Хранить новый run для изменённого поставщика и исходные run остальных. Кнопка «Вернуть исходный» восстанавливает полный исходный набор. Следующий сценарий рассчитывать от base, без накопления предыдущей задержки.
6. Если оставить «Все поставщики» для изменения спроса — вызвать отдельный demand-only сценарий каждого run. Если задержка всех партий действительно нужна для MVP, сначала расширить серверный контракт и движок вместе с участником 2; текущий endpoint этого не делает.

Разбор текста: `POST /api/scenarios/parse` принимает `run_id`, `text`, `selected_shipment_id`. Сейчас `Gateway.parseScenario` не передаёт run — изменить его сигнатуру и вызов. Сервер возвращает `scenario`, `question`, `needs_clarification`, `requires_confirmation`, `status`. Сопоставить с UI, при уточнении/ошибке не применять параметры; после распознавания дождаться кнопки «Сравнить сценарии».

### P0. Заказ — сохранить ручную правку и версии

Текущий `OrderModal.tsx` передаёт `lines` в создание и сразу вызывает approve. На сервере процесс другой:

```text
POST  /api/orders                     {run_id, supplier_id, skus:[...]}
PATCH /api/orders/{draft_id}           {version, changes:[{sku, approved_qty, reason}]}
POST  /api/orders/{draft_id}/approve   {version, acknowledge_warnings:true}
GET   /api/orders/{draft_id}/export.csv
```

Капитан реализует orchestration в адаптере/состоянии модалки:

1. Для каждой вкладки поставщика использовать его настоящий run. Создать draft из SKU.
2. Отправить PATCH для изменённых пользователем количеств. Причина на сервере минимум 3 символа; синхронизировать эту проверку UI. Количества/MOQ/кратность/коэффициенты проверяет сервер.
3. Сохранить draft_id и последнюю version сразу после каждой успешной операции. При неудаче PATCH/approve повторять соответствующий шаг с сохранённым draft, а не создавать новый заказ.
4. Показать фактические предупреждения и отдельное подтверждение их просмотра. Только после действия пользователя отправлять `acknowledge_warnings:true`. Не выставлять true незаметно ради обхода 422. `blocked`/approval_blockers таким подтверждением не снимаются.
5. При 409 перечитать `GET /api/orders/{id}`, показать конфликт. При 401 объяснить истечение сессии. Ошибки `error.message` уже читаются общим транспортом, `error.fields` желательно показать рядом со строкой.
6. Версию брать из ответа, не прибавлять самостоятельно. Экспортировать **утверждённый** snapshot через Bearer fetch → Blob; имена файлов и поля поставщика проверить. Без автоматической отправки поставщику.

Контроль: исходно `00001=156`, вручную `168` с причиной, серверный CSV содержит `168`, повторное открытие не теряет утверждённое значение.

## 4. ИИ: три отдельные функции, проверить каждую

| Функция | Endpoint | Что проверить |
|---|---|---|
| Объяснение карточки | `POST /api/runs/{id}/explain` | Ответ содержит `status`, UI ждёт `mode`: преобразовать. `provider` может быть null. Сервер выбирает факторы и формирует проверяемый текст |
| Разбор сценария | `POST /api/scenarios/parse` | Нужны run и выбранная партия, human confirmation |
| Свободный чат | `GET /api/assistant/status`, `POST /api/assistant/messages` | Реальная модель отвечает, показывает корректный статус, переходы работают, ключ не попадает в браузер |

Чат уже реализован: `backend/app/ai/assistant.py`, `frontend/src/lib/assistant.ts`, `frontend/src/components/Assistant.tsx`. База знаний `KNOWLEDGE` хранит описание навигации и расчётов. Обновить её после добавления выбора партии и подтверждения предупреждений.

Сейчас чат получает **снимок браузера**, а не проверенные серверные run. Для конечной интеграции желательно передавать идентификаторы доступных run и выбранный SKU; сервер проверяет принадлежность сессии и формирует факты сам. Пока снимок оставлен — явно сохранять эту границу, не представлять его как независимую серверную проверку. После интеграции единиц добавить `stock_unit` и коэффициент в обе модели контекста чата; текущая ScreenProduct содержит только `unit`.

Смена run/dataset уже сбрасывает диалог. История сохраняется при переключении разделов; история вкладки не заменяет постоянное хранилище. Помощник не применяет действия и не рассчитывает количества самостоятельно. Ссылки допускаются только на известные разделы/SKU.

В серверном `.env`:

```dotenv
ENGINE_MODULE=app.engine.service
IMPORTER_MODULE=app.importers.service
AI_PROVIDER=openai
OPENAI_API_KEY=<реальный ключ>
OPENAI_MODEL=<модель с доступом у команды>
AI_RESPONSE_FORMAT=json_schema
ALLOW_REAL_AI=false
```

Альтернатива: `AI_PROVIDER=nvidia` + `NVIDIA_API_KEY`, `NVIDIA_MODEL`, `NVIDIA_BASE_URL`. Для JSON-only модели использовать `AI_RESPONSE_FORMAT=json_object`. Общие `AI_API_KEY/AI_MODEL/AI_BASE_URL` имеют приоритет; проверить, что старые значения не перекрывают выбранного провайдера. Ключи — только в `.env` сервера, не в Git и не в `VITE_*`. После изменений перезапустить API.

`ALLOW_REAL_AI=false` разрешает обращения по synthetic и блокирует передачу реальных данных внешней модели. Для согласованной работы с данными компании явно включить true. Значение `ai_configured=true` сообщает только о наличии настроек, не доказывает успешный вызов. Обязательно проверить `status=generated` настоящим запросом, а затем поведение без доступа к провайдеру. Подробности: [ASSISTANT.md](ASSISTANT.md).

## 5. Данные и импорт

Для первого сквозного прохода использовать `demo-engine-v1` с API: это проверяет серверный движок и не требует реальных файлов. Затем подключать данные компании через импорт участника 2.

Готовый импортёр поддерживает профиль `qor-explicit-xlsx-v1`: шесть XLSX на одного поставщика с метаданными `_QOR_IMPORT`. Произвольные выгрузки 1С/CSV автоматически не поддерживаются. За таблицу соответствия колонок и бизнес-правила отвечает участник 2, капитан подключает endpoint, права, ожидание результата и выбор dataset.

`POST /api/imports`: Bearer + `X-Admin-Token`; multipart-поля `supplier`, `mapping_version`, `as_of`, `warehouse_id`, повторяющиеся `files`. Не ставить JSON Content-Type на FormData. Ответ 202 → опрос `/api/imports/{id}` до completed/failed/interrupted. После completed использовать dataset_id **в той же сессии**; импортированный набор закрыт другим сессиям.

В текущем UI нет экрана импорта/логина администратора. На MVP можно оставить импорт отдельной процедурой капитана, но тогда нужна явная серверная публикация разрешённого демонстрационного набора для жюри либо импорт в сессию браузера. Не зашивать admin token в frontend и не передавать его жюри. Нельзя рассчитывать, что файл, загруженный из CLI в одну сессию, появится в произвольной другой сессии браузера.

## 6. Docker и публичная ссылка

Выбрать **один** процесс сборки и раздачи frontend. Рекомендованный вариант для текущего репозитория:

1. Сохранить `api` из корневого `compose.yaml` с persistent volume `/data` и одним worker.
2. Для `web` сделать multi-stage Dockerfile: Node 22 → `npm ci` → build React; финальный Caddy с результатом `frontend/dist` в `/srv` и существующим `deploy/Caddyfile`.
3. В корневом compose перевести web с готового image на этот build. Убрать bind mount `./deploy/web:/srv`, иначе он **перекроет собранный UI**. Сохранить тома сертификатов, HTTPS-порты и зависимость от health API.
4. На build передать `VITE_DATA_MODE=api`, `VITE_API_BASE_URL=`. Это переменные **сборки Vite**: смена runtime env без пересборки JS не переключает приложение. Не включать API-режим на сервере до завершения адаптера.
5. Caddy обслуживает `/api/*` через `api:8000`, остальные пути — SPA с index.html. Проверить, что ошибка API не подменяется HTML страницы.
6. Не запускать одновременно корневой web и отдельный `frontend/compose.yaml` на одном 8080. В Docker использовать DNS `api`, а не localhost для связи между контейнерами.

На Linux создать `.env` из `.env.example` без перезаписи существующих ключей. Минимальная серверная часть:

```dotenv
APP_ENV=production
SITE_ADDRESS=<ваш-домен>
HTTP_PORT=80
HTTPS_PORT=443
CORS_ORIGINS=https://<ваш-домен>
ADMIN_TOKEN=<случайный секрет>
ENGINE_MODULE=app.engine.service
IMPORTER_MODULE=app.importers.service
```

Добавить настройки ИИ из раздела выше. DNS направить на сервер, открыть 80/443. Публичный API и frontend на одном origin; порт backend 8000 наружу не нужен. Для Linux/amd64 и Apple Silicon не копировать host node_modules или виртуальное окружение: зависимости устанавливаются внутри Docker. Сохранить `.dockerignore` и Linux-совместимые окончания строк.

После реализации Docker-сборки UI:

```bash
docker compose up --build -d
docker compose ps
docker compose logs --tail=100 api web
```

При обновлениях не выполнять `down -v`: там база, импорты и сертификаты. До обновления persistent data сделать резервную копию. Итог — HTTPS-ссылка, которая открывается с телефона вне локальной сети, а не `localhost`.

## 7. Проверка до передачи жюри

Из Python 3.12 virtualenv установить обе группы runtime-зависимостей — после merge движок импортируется при старте:

```bash
python -m pip install -r backend/requirements-dev.lock -r backend/requirements-engine.txt

python scripts/export_openapi.py
python scripts/smoke.py --url http://127.0.0.1:8000
```
