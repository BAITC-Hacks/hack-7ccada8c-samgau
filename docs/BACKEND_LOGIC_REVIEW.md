## Как работает backend

| Этап | Что происходит | Код |
|---|---|---|
| Запуск | Проверяется наличие функций модулей, создаётся SQLite, регистрируется публичное демо движка | `backend/app/main.py`, `integration.py` |
| Сессия | Клиент получает токен и отправляет Bearer; объекты разделены по владельцам | `main.py`, `storage.py` |
| Импорт | Посетитель в своей сессии без административного ключа загружает 6 XLSX одного поставщика; проверяются размер, хеши и схема, фоновое задание сохраняет DatasetPayload | `main.py`, `importers/service.py`, `xlsx.py`, `assemble.py` |
| Расчёт | Очищаются разовые покупки, восстанавливается спрос при stockout, учитываются сезонность, рост, остаток, поставки, MOQ и единицы | `engine/demand.py`, `calculator.py`, `service.py` |
| Сценарий | Создаётся новый run с заменой параметров сценария; старые расчёты и заказы сохраняются | `main.py`, `engine/service.py` |
| Заказ | Создание → правка количества с причиной → проверка версии, блокеров, MOQ и предупреждений → утверждение | `main.py`, `orders.py` |
| Экспорт | CSV утверждённого снимка с фактически согласованными количествами | `orders.py` |

SQLite уже подключается капитанским API: `storage.Store`, по умолчанию
`data/qor.sqlite3`. Участник 2 возвращает данные/результаты и не открывает БД.
Капитан отвечает за настройки хранения и постоянный том при развёртывании.

## Где и что делает OpenAI

`backend/app/ai/adapter.py` → `AIAdapter.request()` отправляет HTTPS POST
на `<base_url>/chat/completions` через httpx. Ключ остаётся на backend.
Провайдер, модель и ключ выбираются настройками из `backend/app/config.py`.
`run.py` загружает корневой `.env`; переменные процесса имеют приоритет.

1. **`POST /api/scenarios/parse`**: модель переводит текст в ID партии,
   задержку и процент изменения спроса либо запрашивает уточнение. Сервер
   проверяет типы, диапазоны и принадлежность партии. Возвращается
   `requires_confirmation=true`; UI должен показать параметры и только после
   действия пользователя отдельно вызвать `/api/runs/{id}/scenario`.
2. **`POST /api/runs/{id}/explain`**: модель выбирает 1–8 существующих кодов
   факторов. Сервер отвергает неизвестные/повторные коды и собирает объяснение
   по шаблону из рассчитанных значений. Свободный текст объяснения модель
   сейчас не пишет. Ответ честно помечен `rendering=verified_template`.

ИИ не считает итоговое количество, не утверждает заказ и не отправляет его
поставщику. При ошибке возвращается `status=fallback`, доступны локальное
объяснение и ручной сценарий. Успех модели помечается `status=generated`.

Есть JSON Schema/Pydantic-проверки, сетевой таймаут 12 секунд, общий 15 секунд,
ограничение ответа 64 KiB, лимит 10 ИИ-запросов в минуту на сессию и кэш
объяснений по владельцу/run/SKU/языку. Повторов сетевого запроса нет.
Реальные наборы не отправляются провайдеру при `ALLOW_REAL_AI=false`.
Даже синтетические XLSX, загруженные через импорт, получают `mode=real`;
для публичного ИИ-демо следует выбирать доверенный `demo-engine-v1`.

- Эффективный ключ: присутствует; модель: `gpt-6-luna`.
- Endpoint соответствует стандартному OpenAI `/v1`, формат `json_schema`.
- `ALLOW_REAL_AI=false`.
- Оба модуля: `app.engine.service`, `app.importers.service`.

Ранее ключ и модель были пустыми; после сохранения `.env` это исправлено.
Нужно перезапустить уже работающий backend, чтобы он прочитал изменения;
настройки существующего процесса этим обзором не проверены. Непустые
`AI_API_KEY`/`AI_MODEL` имеют приоритет над `OPENAI_*`. Значения
секретов в документацию, Git или VITE-переменные не помещать.
`/api/health` с `ai_configured=true` означает наличие настроек, а не успешную
аутентификацию у провайдера или совместимость выбранной модели.

## Что нужно устранить или подтвердить

1. **ИИ настроен, живой вызов ещё не подтверждён.** После перезапуска
   необходим настоящий успешный вызов на синтетическом наборе. Готовый
   `scripts/ai_smoke.py` проверяет `generated` и правильные параметры;
   fallback не считается успехом. Сейчас скрипт не запускался.
2. **Frontend ещё несовместим с API в прочитанной версии.**
   `frontend/src/lib/api.ts` использует cookie, ожидает массив datasets,
   отправляет supplier=null для всех, parse без run_id и создание заказа
   через lines. Backend требует Bearer, `{items}`, отдельный run на поставщика,
   run_id для parse и skus для заказа. Простого переключения VITE_DATA_MODE
   недостаточно. Сверять также статусы, summary, trajectory и approve.
   Источник контракта: `docs/FRONTEND_HANDOFF.md`, `docs/openapi.json`.
   Старый `frontend/INTEGRATION.md` описывает ожидания UI и должен быть согласован.
3. **Ответы на казахском пока не реализованы в explain.** Запрос принимает kk,
   но сервер всегда возвращает русский шаблон с `language=ru`. Это ограничение
   относительно требования ТЗ об ответах ИИ на казахском по запросу.
4. **В запросе провайдеру нет явного лимита токенов генерации.** Ограничение
   чтения ответа в байтах не является лимитом генерации у провайдера.
   Капитану стоит задать подходящий выбранной модели лимит и проверить его
   поддержку, чтобы ограничить расход токенов и ожидание.
5. **Границы данных:** текущий импорт требует `_QOR_IMPORT`, реальные форматы
   поставщиков и 250 тысяч строк не проверены. Нельзя заявлять универсальную
   загрузку Excel/CSV или подтверждённое качество прогноза на реальных данных.

Статический просмотр показывает согласованную цепочку backend, но не доказывает
доступность работающего сервера, провайдера или успешную работу в браузере.

## Повторный обзор четырёх ловушек

| Ловушка | Механизм в коде | Граница применимости |
|---|---|---|
| Разовая покупка | `demand.clean_orders`: объединение документов, медиана/MAD, затем клиент за день/месяц; сохраняется исключённая часть | Для документного порога нужно минимум 8 прошлых наблюдений. Повторные большие покупки в трёх неделях сохраняются с предупреждением; это эвристика, а не доказанный устойчивый рост |
| Stockout | `reconstruct_demand`, `build_history`: сначала очистка выбросов, затем восстановление по дням наличия; пересечения интервалов не удваиваются | Требуются интервалы отсутствия. При менее 7 днях наличия нужна историческая опора; иначе спрос неизвестен. Месячный нулевой остаток не позволяет восстановить точные даты |
| Сезонность/рост | `forecast_level`, `calculator`: нормализация 12 коэффициентов, медианная база, сравнение месяцев год к году, подтверждённый прирост, дополнительный сценарный множитель | Профиль поставщика приближённо применяется к SKU. При короткой истории дополнительный подтверждённый рост не применяется поверх уже выросшего текущего уровня; есть предупреждение |
| Товар в пути | `calculator`: только подтверждённые партии после даты расчёта и до конца горизонта; перевод единиц, задержка конкретной строки | Просроченные партии требуют сверки; неизвестная полнота поступлений блокирует утверждение. Партии после горизонта не уменьшают текущий заказ |

Дополнительно просмотрены `assemble.py`, `engine/service.py`, обработчики
сценариев/ИИ и `orders.py`: детализация и месячные итоги не складываются,
неизвестный остаток не становится нулём, резерв не вычитается дважды,
MOQ применяется после перевода единиц, ручное количество не обходит блокеры.
В этих просмотренных путях нового подтверждённого дефекта не установлено;
общей гарантии корректности без исполнения и реальных данных это не даёт.

Модель `gpt-6-luna` существует и поддерживает Chat Completions и Structured
Outputs по [официальной документации](https://developers.openai.com/api/docs/models/gpt-6-luna).
Доступность конкретному ключу не проверена. Код не задаёт reasoning effort;
для этой модели документирован default medium, поэтому укладывание в 15 секунд
следует подтвердить отдельно. В текущем адаптере нет function calling.
